# Data quality: emoji/feeling coverage + provenance metadata

Date: 2026-09-01
Status: approved design, pre-implementation

## Problem

Emoji predictions are dominated by gesture/emotion emojis. For "I want to
watch TV" the top-10 is `🚶 🥰 👀 🙂 👋 ❤️ 🤔 🌟 🤝 💪` — no `📺`. Concrete
objects, nouns, activities, food, places, etc. are underrepresented.

Root cause is in `tools/data/train.ts`'s `GEN_PROMPT`: it spreads generated
texts across *senders, moods, intents, lengths* but has **no topical axis**.
Generated texts skew conversational/emotional, so the annotator only ever sees
material for gesture/emotion emojis. Frequency-ranked `labels.ts` then never
promotes object emojis into `labels.json`, so the model has no class for them.

Secondary: the two rare-label upsamplers (`tools/data/emoji2feeling.ts`,
`tools/data/feeling2emoji.ts`) were deleted in commit `b008c0e` (the pipeline
migration) and are stale — they read/write the removed `data.jsonl`, emit no
`bg`/`fg` colors (so `data.py:read` would silently drop every row), annotate
against a closed feeling list with a "prefer Neutral" guidance block, and don't
use the shared `annotate()` module.

There is also no per-row provenance, so bad data can't be sliced or quarantined
later.

## Scope

Code only. This lands the scripts, prompt change, config bump, metadata field,
and docs. The maintainer runs the (paid, slow) Bun generation scripts,
`bun run labels`, and training separately.

Out of scope: any training/export code, `labels.json` contents (regenerated by
`bun run labels` after the corpus grows), `stat.ts`, and the actual data-cleaning
tool (deferred — the `meta` field added here is the groundwork for it).

## Design

### 1. `tools/data/meta.ts` (new)

Single helper so every writer stamps provenance identically.

```ts
export function rowMeta(fields: {
  src: string
  v: number
  topic?: string
  target_emoji?: string
  target_feeling?: string
  params: Record<string, unknown>
}): Record<string, unknown>
```

Returns a `meta` object:

```json
{
  "src": "train",
  "v": 1,
  "at": "2026-09-01",
  "model": "openai/gpt-5.6-luna",
  "topic": "kitchen & cooking",
  "params": { "batchSize": 50, "minLen": 4, "maxLen": 48 }
}
```

- `at` — `YYYY-MM-DD` (UTC) at run time.
- `model` — imported from `annotate.ts` (`MODEL`).
- `topic` — present only for `train.ts` rows.
- `target_emoji` / `target_feeling` — present only for the matching upsampler.
- `v` — per-script schema/logic version, starts at `1`, bumped by hand when a
  script's generation or annotation logic changes materially. Convention
  documented in `CLAUDE.md`.
- Undefined optional keys are omitted from the output object.

The caller (not `annotate()`) builds `meta`, because only the caller knows
`src` / `topic` / `params`.

Row shape written to `train.jsonl`:

```json
{"text": "...", "feeling": "...", "emoji": "...", "bg": ["#..","#.."], "fg": "#..", "meta": { ... }}
```

Existing `train.jsonl` rows are **not** backfilled. `data.py:read` matches
`case {"text", "emoji", "feeling", "bg", "fg"}` — a mapping pattern that ignores
extra keys and is unaffected by `meta` being present on some rows and absent on
others. Confirmed against `data.py` as committed.

### 2. `tools/data/train.ts` — topical axis

- Add a `TOPICS` array of ~24 concrete domains, e.g.: food & cooking, chores &
  home, commute & travel, weather, pets & animals, tech & devices, shopping &
  money, TV & film, games, sports & exercise, health & body, school & studying,
  work & office, music, clothes, events & celebrations, hobbies & crafts,
  outdoors & nature, phones & logistics, eating out & delivery, cars, news,
  family & relationships, plans & scheduling, small talk & random. A few
  inherently-emotional topics stay in the list so the mood spread does not
  collapse.
- Assign each of the `BATCH_COUNT` batches a topic round-robin.
- `genBatch(topic)` prompt = the current constraints **plus**: "every message is
  about {topic}; do not announce the topic; sound natural; still span moods,
  intents, and lengths."
- Carry `topic` alongside each generated text (array of `{ text, topic }` instead
  of a bare string array).
- Write `meta` via `rowMeta({ src: "train", v: 1, topic, params: { batchSize:
  BATCH_SIZE, minLen: MIN_LEN, maxLen: MAX_LEN } })`.
- No dedup, no normalize/length pre-filter (unchanged from today).

### 3. `tools/data/upsample-emojis.ts` (new; supersedes `emoji2feeling.ts`)

Purpose: grow coverage of rare **palette** emojis.

1. Load `labels.json` → `emojis` palette.
2. Read `train.jsonl` via `io.ts:readJsonl`; count rows per palette emoji
   (emojis outside the palette ignored; palette emojis with no rows count 0).
3. `targets` = `RARE_EMOJI_COUNT` (default 60) rarest palette emojis, rarest
   first, ties keep `labels.json` order. Only emojis in `labels.json` are ever
   targeted.
4. Per target, `PQueue`-parallel (`GEN_CONCURRENCY`) `genBatch(voice, emoji)` →
   `TEXTS_PER_EMOJI` (default 40) short messages that fit that emoji's subject or
   mood, with the emoji never emitted or named. `voice` drawn from `VOICES`
   (ported from the original).
5. Collect **every** generated `{ text, target_emoji, voice }`. No dedup, no
   length filter.
6. Run the shared `annotate(texts)` → `Map<index, { emoji, feeling, bg, fg }>`
   (open-set labels + colors, one retry per batch, same as `train.ts`).
7. For every index that annotated successfully, append one row to `train.jsonl`:
   `emoji` / `feeling` are `annotate()`'s free choice; `meta` via
   `rowMeta({ src: "upsample-emojis", v: 1, target_emoji, params: { voice,
   textsPerEmoji: TEXTS_PER_EMOJI } })`.
8. Print a summary (targets, generated, annotated→train, dropped-no-annotation).

Dropped from the original: `data.jsonl` I/O, the self-contained closed-list
feeling annotation, `FEELING_GUIDANCE`, the local `normalize`, dedup against the
corpus, the `MAX_TEXT_LEN` pre-cut, the `gen_labels.ts` reference.

### 4. `tools/data/upsample-feelings.ts` (new; supersedes `feeling2emoji.ts`)

Same shape as §3, seeded by the rarest **palette feeling**.

1. Load `labels.json` → `feelings` list + `emojis` palette.
2. Read `train.jsonl`; count rows per palette feeling, counting only rows whose
   emoji is also in the palette (matches the original's `rarestFeelings`).
3. `targets` = `FEELINGS_PER_RUN` (default 3) rarest palette feelings, ties keep
   `labels.json` order. Only feelings in `labels.json` are targeted.
4. `BATCHES_PER_FEELING` (default 20) batches per target, round-robin, each
   `genBatch(voice, feeling)` → `GEN_BATCH_SIZE` messages conveying that feeling.
5. Collect every generated `{ text, target_feeling, voice }`. No dedup, no filter.
6. Shared `annotate(texts)`.
7. Append every annotated row: `feeling` / `emoji` are `annotate()`'s free
   choice; `meta` via `rowMeta({ src: "upsample-feelings", v: 1, target_feeling,
   params: { voice, batchesPerFeeling: BATCHES_PER_FEELING } })`.
8. Summary.

Dropped from the original: `conveyInstruction` / `FEELING_GUIDANCE`, closed-list
annotation, the "feeling drift" reject step, `data.jsonl` I/O, `normalize`,
dedup, `gen_labels.ts` reference. Whatever `annotate()` returns is written; the
only filter is `data.py:read` at load time.

### 5. `tools/data/re-annotate.ts` — metadata

Stamp `meta` via `rowMeta({ src: "re-annotate", v: 1, params: { sampleSize:
SAMPLE_SIZE } })` on both rows it emits per source line (the new-label row and,
when labels changed, the kept-old-label row). No `topic`. No other behavior
change.

### 6. `tools/data/config.ts`

`TOP_EMOJIS` 150 → **200**. `TOP_FEELINGS` unchanged at 32.

### 7. `package.json`

Add aliases:

```json

"upsample-feelings": "bun run tools/data/upsample-feelings.ts"
```

## Data flow

```
train.ts:        TOPICS round-robin -> genBatch(topic) -> texts[{text,topic}]
                   -> annotate() -> {emoji,feeling,bg,fg} -> train.jsonl + meta{src:train,topic}

upsample-emojis: labels.json emojis -> count in train.jsonl -> N rarest
                   -> genBatch(voice,emoji) x targets -> texts
                   -> annotate() -> train.jsonl + meta{src:upsample-emojis,target_emoji}

upsample-feelings: labels.json feelings -> count in train.jsonl -> N rarest
                   -> genBatch(voice,feeling) -> texts
                   -> annotate() -> train.jsonl + meta{src:upsample-feelings,target_feeling}

re-annotate.ts:  data.jsonl sample -> annotate() -> train.jsonl + meta{src:re-annotate}

load (data.py):  read() filters empty / >MAX_TEXT_LEN text, out-of-palette
                 emoji/feeling. meta ignored.
```

## Error handling

- `annotate()` keeps its existing behavior: one retry per failed batch, missing
  map entries = that text is dropped (no row written). Unchanged.
- A generation batch that throws is logged and skipped (as in `train.ts` /
  the originals).
- Upsamplers exit non-zero only on unreadable `labels.json` / `train.jsonl`.
- No transactional guarantee across the append; `appendJsonl` is best-effort,
  matching the current scripts.

## Testing / verification (no training run)

- `bunx tsc --noEmit` clean over `tools/`.
- `uv run ruff check .` and `uv run ruff format --check .` (no Python changes,
  cheap regression check).
- Hand-write one `meta`-tagged line into a scratch `.jsonl` and confirm
  `python -c "import data; list(data.read('scratch.jsonl'))"` parses it and that
  a row with an out-of-palette emoji is still dropped.
- Dry-run each new script with generation stubbed / `BATCH_COUNT` tiny is
  optional and costs gateway credits — left to the maintainer.

## Risks

- Generating without a length pre-filter wastes annotation spend on texts that
  `data.py` later drops for length. Accepted deliberately: keeps the raw
  generated corpus intact and lets `meta` drive cleanup later.
- Topic anchoring could reduce mood diversity if the topic list skews concrete.
  Mitigated by keeping emotional topics in `TOPICS` and keeping the existing
  mood/intent/length spread language in the prompt.
- `TOP_EMOJIS = 200` enlarges the emoji head / InfoNCE table; only takes effect
  after `bun run labels` + retrain, both maintainer-run.
