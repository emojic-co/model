# About this model

`emojify.ing` turns a short piece of text into a styled emoji card. A single
small character-level network reads the raw string and predicts everything on
the card at once.

## What the model does

Given up to 42 characters of text, the model produces three things in one
forward pass:

- **Emojis** — a ranked multi-label set (a phrase can map to several emojis, or
  to none).
- **Styles** — a ranked multi-label set from a fixed vocabulary; each style
  selects a font and an animation in the web app.
- **Colors** — a small conditional GAN samples five `{bg1, bg2, text_color}`
  palettes for the text, so every prediction offers a few colorways.

It is character-level and trained from scratch: no tokenizer, no pretrained
embeddings, no external language model at inference time. The whole thing runs
in the browser via ONNX Runtime Web.

## Outputs

| Output | Type | Size |
| --- | --- | --- |
| Styles | multi-label | 21, fixed closed set |
| Emojis | multi-label | ~770, frequency-derived vocab (dynamic) |
| Colors | regression (GAN) | 5 palettes × 9 values (3 sRGB colors) |

The style set is fixed and closed — the annotator must pick from 21 labels. The
emoji vocabulary is open in the corpus (any emoji can be annotated) and the
shipped vocabulary is simply every emoji that clears a minimum kept-record count
during the data rebuild, so it grows as the corpus grows.

The shipped inference graph is roughly **0.4M parameters** (encoder + emoji head
+ style head + color generator); a training-only critic adds ~0.07M.

## Compared to keyword search

The web app has a **model / keywords** toggle so the two approaches sit
side by side. Keyword search maps each word to emojis via a lookup table built
from CLDR emoji annotations — zero training, fully interpretable, instant, but
it only fires on literal word matches.

On the CLDR keyword probe (each CLDR keyword as the query, its annotated emojis
as the target):

| | acc@1 | acc@10 |
| --- | --- | --- |
| Keyword lookup (CLDR baseline) | 0.37 | 0.58 |
| Model | *(same probe)* 0.62 | 0.81 |

On the held-out eval set, a word-overlap baseline scores acc@1 0.25 / acc@10
0.54 against the model's 0.63 / 0.83. The model wins because it generalizes to
paraphrase, tone, negation ("not good"), and phrasings that share no words with
any keyword. Keyword search remains a good fallback when you want a predictable,
explainable mapping.

## The data

- **Master corpus:** ~288k rows, append-only. Every row is a short text plus its
  annotated emojis, styles, and a `bg`/`fg` palette.
- **How it is built:** short texts are generated by an LLM across ~24 concrete
  topics and a broad spread of persona / mood / intent / length, then annotated
  by an LLM (emojis, styles from the fixed set, a color palette). Targeted
  upsampling passes add coverage for rare emojis, negation, specific colors, and
  keyword-driven slices.
- **Rebuild:** a deterministic, seeded pass collapses near-duplicate texts,
  caps how many rows any one emoji can dominate, derives the emoji vocabulary,
  and splits into **~120k train / 2.5k eval** rows.
- Texts are normalized before training: whitespace collapsed, lowercased, runs
  of 3+ identical characters clipped to 2, out-of-vocabulary characters dropped.
  Most texts are 20–35 characters.

## Model architecture

**Shared text encoder**

1. Character embedding (index 0 reserved for padding).
2. Three `Conv1d` blocks with dilations `1, 2, 4` and channel widths
   `120 → 200 → 300`, each spectral-normalized with a LeakyReLU. Length is
   preserved throughout — no pooling between blocks.
3. Padding positions are masked to `-inf`, then a single global max-over-time
   produces a 620-dimensional text embedding.

**Heads**

- **Style head** and **emoji head** are structurally identical: dropout → a
  bias-free linear projection into a small embedding space (16 for styles, 64
  for emojis) → dot product against a learned per-label embedding table → one
  logit per label. Both are trained as retrieval with a multi-positive
  Log-Sum-Exp InfoNCE loss and both backpropagate into the encoder.
- **Colors** are a conditional GAN, not a head. The generator mixes the (frozen)
  text embedding with unit-norm noise and emits 9 sRGB byte offsets; a
  dual-branch dot-product critic scores palettes in OKLab space. The generator
  loss is the positive contrastive term only. An OKLab energy distance between
  generated and real palettes is the early-stop metric but is never
  backpropagated.

## Performance

From the most recent training report (held-out eval set, 2.5k rows):

**Emojis** — retrieval accuracy@k

| k | 1 | 3 | 5 | 10 |
| --- | --- | --- | --- | --- |
| Eval set | 0.63 | 0.76 | 0.80 | 0.83 |
| Keyword probe | 0.62 | 0.74 | 0.78 | 0.81 |
| CLDR probe | 0.37 | 0.48 | 0.53 | 0.58 |

**End-to-end gold cards** (125 rows, running the full shipped graph):

| k | 1 | 3 | 5 | 10 |
| --- | --- | --- | --- | --- |
| Emoji acc@k | 0.76 | 0.86 | 0.88 | 0.91 |
| Style acc@k | 0.62 | 0.82 | 0.91 | 0.97 |

**Colors** — palette accuracy (OKLab distance below threshold), by target color:
green 0.92, bright 0.96, blue 0.60, red 0.48, dark 0.20 (overall 0.63). Warm and
dark palettes are the current weak spot.

Numbers move whenever the corpus grows; treat these as a snapshot.

## Training

- **Framework:** PyTorch Lightning.
- **Hardware:** a 16-core CPU container on Modal — **no GPU**. The model is
  small enough that CPU training is practical.
- **Schedule:** stage 1 trains the encoder + style + emoji + critic heads
  (up to 500 epochs, early stopping on emoji retrieval MRR / an emoji+critic F1
  when both are on, patience 20, validating every 100 steps). Stage 2 freezes
  the encoder and trains the color GAN (up to 300 epochs, early stopping on the
  OKLab energy distance). Batch sizes are 256 (stage 1) and 512 (stage 2).
- **Time & cost:** a full run is on the order of tens of minutes of wall time
  and well under ~$1 of CPU compute per run. Runs are cheap enough to repeat
  often as the corpus is upsampled.
- Every run ends by regenerating the browser assets (`model.onnx`, `meta.json`,
  `config.json`) and a full HTML report.
